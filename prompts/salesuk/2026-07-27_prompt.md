# Context
Discovered while investigating UK Meta/Facebook orders: comparing order names across the main dashboard's six January UK tabs (Kamsi, Dilaksi, Sukirtha Email, Sajeepan, Sonya, DM) showed 1,037 of 2,156 unique orders (48%) counted in more than one tab — because SEO tabs are product-scoped while Ads tabs are utm-scoped, and the same order can satisfy both.

# User's literal instructions (paraphrased across several messages)
1. "in mind every task no duplicate any single or do not overlap in others" — every group on the new page must be mutually exclusive.
2. "create a new page for saluk.html ... dont use sales.js create new salesuk.js" — deliberately separate file, no shared code/state with the main dashboard backend.
3. "add a tab for january only and in january tab add tab for DM-Ad" — DM-Ad group: `Shop_DM_PMax-46_AguAsset` + `Shop_DM_PMax-25` combined.
4. "no need product id add by order id with all the details with all sessions details" — order-level rows (not line-item/product rows), full session history via an expandable panel.
5. Follow-up: "now create a next tab for meta" with an explicit list of campaign/source values (deduped to: Sales Ads, Sales Ads – Copy, Sales Ads | Retargeting | Add to Cart, Facebook, Instagram, android-app://m.facebook.com/).
6. "the meta tab is too much loading do like what you done for dm tab" — apply the same static-snapshot performance fix already used for DM-Ad.

# Outcome
`api/salesuk.js` (new, self-contained) + `pages/salesuk.html` (new). `GROUPS` array checked in a fixed priority order (DM-Ad then Meta) — `assignGroup()` returns the first match, guaranteeing no order can land in two groups by construction. Static-snapshot fast path mirrors the pattern already used across `api/sales.js`'s historical-month tabs. See `reports/salesuk/2026-07-27_summary.md` for current numbers and `evidence/salesuk/2026-07-27_standalone-order-level-page.md` for full implementation detail.
