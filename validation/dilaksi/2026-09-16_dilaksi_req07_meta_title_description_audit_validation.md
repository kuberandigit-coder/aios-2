## Purpose
Validate Dilaksi Requirement 07 (Meta Title & Description Audit).

## Checks performed
1. **Correct Shopify source used** — `graphql("ledsone_uk", ...)`, the existing `shopify_client.py`, current `seo.title`/`seo.description` fields (confirmed against `dev_tasks/geo_visibility/shopify.py`'s existing usage before assuming field names). No scraping. Live run returned 5,533 real pages (5,043 products + 490 collections).
2. **Correct GA4 source used** — existing `google_client.py`'s `fetch_ga4_report`, same `GA4_PROPERTY_ID = "408110563"` and organic-only convention Dilaksi's own Req1/Req2 already use. Live run returned 2,250 real paths with sessions (top path `/` with 1,161 sessions, verified plausible).
3. **Missing metadata detection verified** — 1,023 missing titles / 1,519 missing descriptions found on real live data; spot-checked example (`.../conduit-lighting` collection) confirmed both fields genuinely null in the Shopify response.
4. **Duplicate detection verified** — 98 duplicate-title groups / 128 duplicate-description groups found; sample group `"Steampunk Water Pipe Table Lamp-E27"` confirmed to genuinely span 2+ different product URLs, and blank/null values confirmed NOT to form a group (code path: `if not value: continue` before grouping) — no product ever counted as its own duplicate (group filtering excludes the page's own `shopifyId` from its `duplicateUrls`).
5. **Length rules verified** — exact >60 / >150 character thresholds applied; live run found 1,512 / 1,965 real violations; one sample title measured at 82 characters, correctly flagged.
6. **Priority rules verified** — all 4 documented rules plus the Phase 7 missing+low-traffic→MEDIUM mapping implemented and traced: live HIGH example (`.../conduit-lighting`) = missing meta + real high GA4 traffic; live multi-issue example (a product with both a length issue and a missing description) correctly took the higher applicable priority (missing-meta rule over length-only rule) rather than double-counting or averaging.
7. **Multiple issues on one URL** — 2,510 real pages had 2+ simultaneous issues in the live run; each retained every individual issue in its `issues[]` list while still receiving one single, correctly-highest priority.
8. **High-traffic / low-traffic missing metadata** — both paths exercised live: the one real HIGH-priority page had genuine high GA4 traffic; MEDIUM-priority missing-meta pages (2,232 of them) were pages either below the 50-session threshold or with no GA4 match at all.
9. **GA4 URL matching / no-GA4-data path** — confirmed both branches: matched paths return a real integer session count; unmatched paths return `null`/"No GA4 data", never a fabricated zero (code path: `sessions_by_path.get(path)` returns `None` when absent, and `_classify_traffic(None, ...)` returns `"No GA4 data"` explicitly, short-circuiting before the threshold comparison).
10. **No fabricated data** — every number in this evidence set traces to a live Shopify or GA4 API response; `ga4Error` field exists specifically so a GA4 outage degrades to "No GA4 data" everywhere rather than silently substituting fake numbers (mirrors the already-proven `GoogleNotConfigured` handling pattern in `dilaksi.py`'s own Req1/Req2).
11. **Filtering** — reviewed `MetaTitleDescriptionAudit.jsx`'s filter logic (page type, priority, traffic classification, field, free-text search) against the real `backlogRows` shape returned by `/backlog` — filter predicates match the actual field names in the API response.
12. **Sorting** — reviewed sort logic for priority (HIGH/MEDIUM/LOW order), GA4 sessions, character count, and URL — each comparator operates on the correct field with a sensible tie-break for `null` GA4 sessions (treated as lower than any real integer).
13. **Audit refresh** — `POST /run` → `already-running` guard (module-level `_AUDIT_STATE`) confirmed to prevent overlapping scans; `GET /status` poll pattern matches this app's established non-blocking background-job convention (`background_job.py` / `alt_text_keywords` router precedent from earlier in this session).
14. **Existing assets checked before creating new ones** — confirmed via grep across `backend/app` (no existing whole-catalog product+collection metadata fetcher; no existing numeric high/low traffic threshold) and across AIOS (`prompts/`, `evidence/`, `validation/`, `closure/`, `handover/`, `source-map/`, `capability/` — no existing Dilaksi Requirement 07 / meta-audit record of any kind) before writing any new code or AIOS record.
15. **Security preserved** — no Shopify token, GA4 service-account JSON, or database password appears in any created/modified file; grepped `dilaksi_meta_audit.py` and this validation set for credential-shaped strings — none found. Frontend only calls this app's own `/api/dilaksi/meta-audit/*` backend routes.
16. **Existing dashboard functionality unaffected** — `python -m py_compile` on `main.py` and `dilaksi_meta_audit.py` passed clean; the new schema-init call is wrapped in the same try/except-per-feature pattern already used for `dilaksi_faq`/`jefri_nonmoving`, so a failure here can only 500 this one new feature, never the rest of the app (same guarantee already relied on elsewhere in this codebase). `npx vite build` passed clean with no new errors (only pre-existing, unrelated `INEFFECTIVE_DYNAMIC_IMPORT` warnings for other files). `DilaksiLayout.jsx`'s existing Req1/2/3/FAQ/Sales panels were only appended to, not altered.
