Currently-active products only: a product only appears here if it had performance data in the last 7 days — not just anytime in the 90-day window. The displayed metrics (Impressions, Clicks, Conv. Value, Cost) still cover the full 90-day window for whichever products remain.

Scope: Jefri's 5 named campaigns (same as Requirement 1), all products with any activity in at least one of the three fixed windows below (not scoped to currently-active products only, since this report is explicitly about period-over-period comparison, including products that may have dropped out).
Periods (fixed calendar quarters, not rolling): Previous 3M = Oct 1 – Dec 31 2025. Last 3M = Jan 1 – Mar 31 2026. Prior-Year 3M = Apr 1 – Jun 30 2025.
ROAS: (Conversion Value ÷ Cost) × 100 for that period; shown as N/A when Cost is 0 for that period (not zero — no spend means ROAS isn't meaningful).
Performance Tier (based on Last 3M only): High = Last 3M ROAS ≥ 400% AND product ranks in the top 20% by Last 3M Conv. Value among all products with Last-3M activity. Mid = Last 3M ROAS 200–399% AND product ranks in the 30th–50th percentile by Last 3M Conv. Value. Products matching neither rule show no tier.
Status (Last 3M vs. Previous 3M, using Conv. Value OR ROAS — either metric can trigger it): Improved if either metric's change ≥ +15%. Drop if either metric's change ≤ -30%. Same if either metric's change is between -10% and +14%. A change that falls in none of these bands (or has no Previous-3M baseline to compare against) shows no status — left undefined rather than guessing, since the specification doesn't define that gap.
Known data gap (disclosed, not fabricated): google_ads.product_performance for these 5 campaigns only begins 2025-05-12 — Apr 1–May 11 2025 has zero rows (pre-dates campaign tracking). Prior-Year 3M figures reflect only the real data that exists (May 12 – Jun 30 2025) for products with no earlier April data; this is a genuine source gap, not zeroed-out or estimated figures.
Privacy: no customer data of any kind is used in this report — product-level Google Ads performance only.

Step 1 of T-04 — scope note: this tab only shows the Item ID → Parent Product ID mapping, the first building block of the full T-04 report (Total Sales, Ads Sales, ROAS, Ads Sales % are not in this step). Full discovery/validation for T-04 is in evidence/jefri/T-04-data-discovery.md.
Data source: PostgreSQL (read-only: google_ads.product_performance, listings.shopify_listings, listings.shopify_listings_parent_child_mapping) · fetched via /api/requirement?fn=jefri-req4-mapping.
Scope: every distinct Item ID Jefri's 5 campaigns have EVER had (no date window — "gather all") — not just currently-active products.
Parent Product ID resolution: if the Item ID itself resolves to a Shopify PARENT listing, Parent Product ID = that same Item ID. If it resolves to a Shopify VARIANT (child) listing, Parent Product ID is looked up via listings.shopify_listings_parent_child_mapping. Confirmed live: 100% of matched variants (4,543/4,543) resolve to exactly one parent — no many-to-one conflicts for Jefri's items.
Default row order: grouped by parent — each Parent (Rollup) row is followed immediately by its own Variant rows, then the next parent group. Unmatched rows (no parent to group under) are sorted last. Clicking a column header to sort overrides this grouping.
Unmatched rows (Parent Product ID blank): the Item ID does not correspond to any Shopify product/variant ID in this database at all — confirmed to be 17–20 digit IDs (real Shopify IDs are 13–14 digits), concentrated in one campaign ("Shoparize ALL | All Products"). This is a genuine data gap, not a query failure — these rows are shown, not hidden, so the gap stays visible.
SKU: from listings.shopify_listings.sku. Only populated on Variant rows — Shopify assigns SKU to child/variant listings only, so Parent (Rollup) rows correctly show "N/A (multiple SKUs)" rather than an invented single SKU.
Total Sales (Store): GROSS revenue — SUM(item_price × item_quantity) from order_management.order_item_info, joined to orders where status='Completed' (excludes Refunded/Cancelled/Inprogress/New) and sub_source_id=108 (Shopify ledsone-de). Not net-of-tax — a different "netSales" definition exists elsewhere in this codebase for a different store; which definition T-04 should ultimately use is an open decision, see evidence/jefri/T-04-data-discovery.md. Currently all-time (no date range picker yet, matching this tab's "gather all" scope) — date filtering is a later build step. Parent (Rollup) Total Sales = every Completed order line sharing that Parent Product ID (this already includes all its variants' sales; not separately re-summed from the Variant rows). Shows €0.00 (a real zero) for a matched Parent/Variant with no completed orders — N/A is reserved for Unmatched rows only, where Total Sales genuinely cannot be computed.
Ads Sales / Clicks / Impressions / Cost: from google_ads.product_performance, all-time (same scope as everything else on this tab). For a Parent (Rollup) row these are a true SUM — the parent's own ad entry (if Google ever advertised the parent item directly) PLUS every one of its variants' ad entries, never averaged. Variant and Unmatched rows show that single item's own ad performance. An Unmatched row can still have real Ads data (Google spent money and got clicks on that item ID) even though it has no Shopify match — shown, not hidden.
ROAS: (Ads Sales ÷ Ads Cost) × 100. Shows 0% when both Ads Cost and Ads Sales are 0; shows N/A only in the mathematically undefined case of real Ads Sales with €0 Ads Cost (division by zero, not a real 0%).
Ads Sales % of Total Sales: (Ads Sales ÷ Total Sales) × 100. Shows N/A on Unmatched rows (no Total Sales to divide by) and in the undefined case of real Ads Sales against €0 Total Sales. Known issue, not hidden: discovery testing (see evidence/jefri/T-04-data-discovery.md) found this can genuinely exceed 100% for real products — Google Ads' own conversion-value attribution doesn't always match a fixed Postgres order window 1:1. Treat any figure over 100% as a real finding about the two sources' attribution difference, not a bug in this page.
