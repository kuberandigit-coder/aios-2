Step 1 of T-04 — scope note: this tab only shows the Item ID → Parent Product ID mapping, the first building block of the full T-04 report (Total Sales, Ads Sales, ROAS, Ads Sales % are not in this step). Full discovery/validation for T-04 is in evidence/jefri/T-04-data-discovery.md.
Data source: PostgreSQL (read-only: google_ads.product_performance, listings.shopify_listings, listings.shopify_listings_parent_child_mapping) · fetched via /api/requirement?fn=jefri-req4-mapping.
Scope: every distinct Item ID Jefri's 5 campaigns have EVER had (no date window on the Item ID list itself — "gather all") — not just currently-active products. Total Sales/Ads figures below ARE date-filterable (see Start Date/End Date above) — leaving both blank shows all-time.
Parent Product ID resolution: if the Item ID itself resolves to a Shopify PARENT listing, Parent Product ID = that same Item ID. If it resolves to a Shopify VARIANT (child) listing, Parent Product ID is looked up via listings.shopify_listings_parent_child_mapping. Confirmed live: 100% of matched variants (4,543/4,543) resolve to exactly one parent — no many-to-one conflicts for Jefri's items.
Default row order: grouped by parent — each Parent (Rollup) row is followed immediately by its own Variant rows, then the next parent group. Unmatched rows (no parent to group under) are sorted last. Clicking a column header to sort overrides this grouping.
Unmatched rows (Parent Product ID blank): the Item ID does not correspond to any Shopify product/variant ID in this database at all — confirmed to be 17–20 digit IDs (real Shopify IDs are 13–14 digits), concentrated in one campaign ("Shoparize ALL | All Products"). This is a genuine data gap, not a query failure — these rows are shown, not hidden, so the gap stays visible.
SKU: from listings.shopify_listings.sku. Only populated on Variant rows — Shopify assigns SKU to child/variant listings only, so Parent (Rollup) rows correctly show "N/A (multiple SKUs)" rather than an invented single SKU.
Total Sales (Store): GROSS revenue — SUM(item_price × item_quantity) from order_management.order_item_info, joined to orders where status='Completed' (excludes Refunded/Cancelled/Inprogress/New) and sub_source_id=108 (Shopify ledsone-de). Not net-of-tax — a different "netSales" definition exists elsewhere in this codebase for a different store; which definition T-04 should ultimately use is an open decision, see evidence/jefri/T-04-data-discovery.md. Date-filtered by Start Date/End Date above (order date, inclusive both ends) — blank = all-time. Parent (Rollup) Total Sales = every Completed order line (within the selected range) sharing that Parent Product ID (this already includes all its variants' sales; not separately re-summed from the Variant rows). Shows €0.00 (a real zero) for a matched Parent/Variant with no completed orders in the selected range — N/A is reserved for Unmatched rows only, where Total Sales genuinely cannot be computed.
Ads Sales / Clicks / Impressions / Cost: from google_ads.product_performance, date-filtered the same way (inclusive both ends, blank = all-time). For a Parent (Rollup) row these are a true SUM — the parent's own ad entry (if Google ever advertised the parent item directly) PLUS every one of its variants' ad entries within the selected range, never averaged. Variant and Unmatched rows show that single item's own ad performance for the range. An Unmatched row can still have real Ads data (Google spent money and got clicks on that item ID) even though it has no Shopify match — shown, not hidden.
Date filter mechanics: the Item ID/Parent Product ID/SKU list itself never changes with the date range (all 8,073 items always shown, per explicit instruction) — only the Sales/Ads columns recompute for the selected window. Click Apply after choosing dates, or All-Time to clear both and reset. The default (blank) view is served from a fast static snapshot; any custom date range always queries PostgreSQL live.
ROAS: (Ads Sales ÷ Ads Cost) × 100. Shows 0% when both Ads Cost and Ads Sales are 0; shows N/A only in the mathematically undefined case of real Ads Sales with €0 Ads Cost (division by zero, not a real 0%).
Ads Sales % of Total Sales: (Ads Sales ÷ Total Sales) × 100. Shows N/A on Unmatched rows (no Total Sales to divide by) and in the undefined case of real Ads Sales against €0 Total Sales. Known issue, not hidden: discovery testing (see evidence/jefri/T-04-data-discovery.md) found this can genuinely exceed 100% for real products — Google Ads' own conversion-value attribution doesn't always match a fixed Postgres order window 1:1. Treat any figure over 100% as a real finding about the two sources' attribution difference, not a bug in this page.

Listing ID → SKU: resolved from listings.shopify_listings.item_id/sku (channel: ledsone.de) — the same table/column every other requirement on this page uses. Not guessed, not hard-coded.
Total Sales Since Update: gross line-item revenue (item_price × item_quantity, status='Completed', Shopify ledsone.de) where Order Date ≥ Image Update Date, matched on the listing's own Parent Product ID or Variant ID (same resolution/columns as Requirement 5). Grows automatically as new orders come in — not a static snapshot.
Days Live Since Update = Today − Image Update Date, in whole days (0 if updated today).
Pre-Update Baseline Sales: the SAME NUMBER OF DAYS immediately before the Image Update Date (i.e. exactly Days Live Since Update calendar days) — not a fixed 7/30-day window.
% Change vs Baseline = ((Total Sales Since Update − Pre-Update Baseline Sales) / Pre-Update Baseline Sales) × 100.
Trend thresholds: Improved ≥ +15% · Same −14% through +14% · Dropped ≤ −15%.
Zero-baseline / just-updated handling: if the baseline window is empty (image updated today, Days Live = 0) or Pre-Update Baseline Sales = £0, % Change and Trend are shown as N/A / Insufficient data rather than a fabricated or infinite percentage — same "requires a positive denominator, otherwise N/A" convention already used by muguntha.html's Target Achievement metric.
